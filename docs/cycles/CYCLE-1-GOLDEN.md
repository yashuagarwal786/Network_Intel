# Cycle 1 — functional golden judge flow

## 1. Implemented

The active, read-only prototype opens **VEIL-DEMO-001 / Operation Trinetra / Synthetic Demonstration / Active Review**. It contains 40 typed entities, 40 evidence-linked relationships, 57 evidence records in eight source collections, and fixture-authored Lead 17.

The complete flow is runnable: open case → select/search entities → choose endpoints → compute the Rahul–Vikram path → inspect relationship evidence → open Lead 17 → inspect supporting evidence. Path results fade unrelated records. Entity, relationship, path, lead, source and evidence details share an inspector beside the graph. The graph uses fixed display positions, a readable focused view, and a full-network exploration mode with pan/zoom.

The seven required API endpoints are implemented with Pydantic response schemas and validation. NetworkX computes bounded paths; no fixture stores a hardcoded path response. Unknown entities/evidence/leads and depth-limited/disconnected paths return explanatory 404 errors. Invalid parameters or a traversal depth outside 1–8 return typed 422 errors.

## 2. Technical decisions

- Followed verdict A: retained React, Vite, TypeScript, Cytoscape, FastAPI, NetworkX, theme, and useful interaction patterns. No new dependency was added.
- Moved the earlier monolithic UI and backend into explicitly named legacy files so the active demo could adopt the newly requested case/contracts without deleting earlier work. The existing database file and previous reports were left intact.
- The active backend does not import the legacy database/review handlers or automatic lead rule. It serves fixtures and computes paths only.
- Six deterministic JSON files are generated by `backend/generate_demo.py` and validated by `DemoRepository` at startup. Every entity/relationship/signal has source references; related IDs and source identity are validated.
- Path traversal is an undirected association search using NetworkX bounded breadth-first traversal, maximum eight hops, deterministic node/edge ordering. Returned steps preserve source direction and indicate reverse traversal when needed. Display coordinates never determine the result.
- The target result is exactly Rahul Kumar Sharma → P101 → P204 → Amit Verma → A17 → A31 → Vikram Singh, using USES, CALLED, USED_BY, CONTROLS, TRANSFERRED_TO, CONTROLLED_BY.
- Lead 17 is labelled `generated_by: fixture` and visibly marked FIXTURE LEAD. Its metrics are authored fixtures, with test-only checks against underlying events. No extraction, entity resolution, uploads, NER, new database, or automatic lead detection was implemented.
- The shortest path contains two accounts, A17 and A31. A44 is on a seven-hop alternative via A17 → A44 → A31. The lead explains that distinction explicitly. INR 195,000 is total transfer volume across three transfers, not a claim about distinct funds.
- Phone identifiers are deliberately non-dialable synthetic DEMO numbers. Named files represent canonical synthetic records, not an uploaded or independently verified document collection.

## 6. Known limitations

One synthetic case and one fixture-authored lead. No validated AI model, automatic detection, entity resolution, ingestion, upload, NER, authentication, persistent workflow or deployment. The old database and detector are preserved but not used by the active application. Source files are represented by exact canonical synthetic records rather than imported originals. Review priority is not a probability of criminal activity.

The focused canvas intentionally loads 15 relevant entities by default. Full-network mode loads all 40 and requires pan/zoom; forcing every record into a small viewport would make labels unreadable. The lead inspector scrolls to reveal all five signals and their complete evidence lists. No claim is made that an association path proves chronology, causation or wrongdoing.
